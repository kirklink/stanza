# Stanza: Competitive Landscape Analysis

## The Dart PostgreSQL Ecosystem

The Dart ecosystem for PostgreSQL is surprisingly thin. Most options fall into one of three categories: raw drivers, full ORMs, or lightweight query builders. Stanza sits in the query builder space — a category with very few entries and no dominant player. This is both a challenge (small market) and an opportunity (little competition for the specific niche).

---

## Head-to-Head Comparison

### 1. Raw `postgres` v3 Driver

**What it is:** The official PostgreSQL driver for Dart. Not a query builder — just a connection library with parameterized query execution.

**How objects are created:** Manual. You write SQL, get back `ResultRow` objects, and call `.toColumnMap()` to get `Map<String, dynamic>`. Mapping to Dart classes is entirely your responsibility:

```dart
final result = await conn.execute(
  Sql.named('SELECT * FROM users WHERE id = @id'),
  parameters: {'id': 42},
);
final map = result.first.toColumnMap();
final user = User()..id = map['id'] as int..name = map['name'] as String;
```

**Type safety:** None at the query level. Column names are raw strings, parameters are `Map<String, dynamic>`, result values are `dynamic`. You discover typos and type mismatches at runtime.

**SQL completeness:** Total — you write raw SQL, so anything PostgreSQL supports is available.

**Why someone would choose this over stanza:** Zero abstraction cost, zero learning curve for anyone who knows SQL. For simple apps or one-off scripts, the overhead of annotations + code generation isn't worth it.

**Why someone would choose stanza instead:** As soon as you have more than a handful of queries, the manual mapping code becomes repetitive and error-prone. Stanza eliminates the boilerplate with generated `fromDb`/`toDb` methods and catches field name typos at compile time through typed `Field` getters.

### 2. Drift (formerly Moor)

**What it is:** The most mature and feature-rich database library in the Dart ecosystem. Originally SQLite-focused, with PostgreSQL support added via `drift_postgres`. It's closer to a full ORM than a query builder, though it explicitly markets itself as something in between.

**How tables are defined:** You define tables as Dart classes extending `Table`, using a column builder DSL:

```dart
class TodoItems extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get title => text().withLength(min: 6, max: 32)();
  TextColumn get content => text().named('body')();
  IntColumn get category => integer().nullable().references(Categories, #id)();
}
```

Note the double-parentheses pattern `integer()()` — the first call configures the column, the second finalizes it. This is a common source of confusion for newcomers.

**How objects are created:** Drift generates *two* classes per table: a **row class** (immutable, represents a full database row) and a **companion class** (for inserts and updates where some fields may be absent). You don't write your own entity classes — Drift owns the generated types. You *can* use `@UseRowClass` to map to your own class, but the table definition still uses Drift's DSL, not your class.

```dart
// Generated by Drift:
class TodoItem {       // row class — used for reads
  final int id;
  final String title;
  // ...
}

class TodoItemsCompanion {  // companion — used for writes
  final Value<int> id;
  final Value<String> title;
  // ...
}
```

**Type safety:** Excellent. Column types are enforced at compile time. Where clauses use typed expressions (`u.joinedAt.isBiggerThanValue(since)`). The query builder validates types through the generated column accessors. Drift also has a built-in SQL parser that validates raw SQL queries at compile time.

**SQL completeness:** Very good. JOINs, subqueries, upserts, transactions, GROUP BY, HAVING, DISTINCT, window functions, CTEs. Raw SQL escape hatch with compile-time validation. RETURNING support.

**Additional features stanza doesn't have:**
- Reactive streams (`select(users).watch()` returns auto-updating `Stream`)
- Schema migrations with version tracking
- DAO pattern with `@DriftAccessor`
- Batched statements
- Cross-database (SQLite, PostgreSQL, Web)
- Built-in serialization (toJson/fromJson)
- Compile-time SQL validation

**Downsides:**
- **Heavy**. 5+ packages needed (`drift`, `drift_dev`, `drift_postgres`, `build_runner`, plus database driver). The generated code is substantial.
- **Table-first, not class-first**. You define tables in Drift's DSL, then Drift generates the Dart classes. Your domain models are subordinate to the database schema. If you have existing Dart classes (e.g., from an API layer), you need to add `@UseRowClass` and ensure your class constructor matches Drift's expectations.
- **Learning curve**. The `Value<T>` / `Value.absent()` pattern for companions, the double-parentheses column syntax, the DAO pattern, and the migration system are all Drift-specific concepts.
- **PostgreSQL is second-class**. Drift was built for SQLite. PostgreSQL support comes through `drift_postgres` and doesn't have feature parity. Some PostgreSQL-specific features may not be available through the Dart API.

**How stanza differs philosophically:** Stanza is class-first. You write a normal Dart class, add `@StanzaEntity`, and the generator creates the database mapping *from* your class. You own your domain model. Drift is schema-first — you write the table definition in Drift's DSL, and it generates the domain model for you. This is a fundamental design difference that matters to different audiences.

### 3. Dartonic

**What it is:** A young query builder (v0.0.14, published ~3 months ago) explicitly inspired by Drizzle ORM from the TypeScript ecosystem. Supports SQLite, PostgreSQL, and MySQL.

**How tables are defined:** Schema-first using a builder function. Tables and columns are defined with helper functions, not classes:

```dart
final usersTable = pgTable('users', {
  'id': serial().generatedAlwaysAsIdentity(),
  'name': varchar(length: 100).notNull(),
  'age': integer(),
});
```

**How objects are created:** No code generation. No Dart class mapping. Results come back as `Map<String, dynamic>` (or similar dynamic structures). Column names and table names are plain strings in the schema definition.

**Type safety:** Minimal. Column *definitions* are typed (you can't put `varchar(length: 100)` on a column you intend to store integers), but the *query API* uses string column references:

```dart
final result = await db
    .select({'userName': 'users.name', 'userEmail': 'users.email'})
    .from('users')
    .innerJoin('profile_info', eq("users.id", "profile_info.user_id"));
```

Column names like `'users.name'` are unchecked strings. There's no compile-time verification that these columns exist or have compatible types.

**SQL completeness:** Good for its age. JOINs, RETURNING, transactions, views, WITH clauses, relationships via a `relations()` helper.

**How stanza differs:** Stanza's code generation produces typed `Field` getters (`Animal.$table.name`, `Animal.$table.legs`), so misspelling a column name is a compile error. Dartonic's string-based column references catch nothing until runtime. Stanza also maps results directly to your Dart class instances, while Dartonic returns raw maps.

### 4. Queryflow

**What it is:** A lightweight query builder for MySQL and PostgreSQL. No code generation.

**How tables are defined:** They aren't, formally. You reference table and column names as strings in your queries:

```dart
final result = await queryflow.select('users', ['id', 'name'])
    .where('age', GreaterThan(18))
    .orderBy('name')
    .limit(10)
    .fetch();
```

There is a `TableModel` concept for schema management, but it's optional and doesn't generate typed accessors.

**How objects are created:** Results are `List<Map<String, dynamic>>`. Mapping to Dart classes is manual. There's a `TypeAdapter` system for registering model mappings, but it's runtime-based, not compile-time.

**Type safety:** None at the query level. Every column name is a string. The `Matcher` classes (`GreaterThan`, `Equals`, `Like`, `Between`) provide some structure to where clauses, but they accept `dynamic` values.

**SQL completeness:** Decent. JOINs (inner, left, right, full outer), GROUP BY, HAVING, BETWEEN, IN, DISTINCT, ORDER BY. No RETURNING, no upsert, no CTEs.

**How stanza differs:** Stanza's typed fields and generated entity mapping are the main differentiator. With Queryflow, you trade type safety for simplicity — no annotations, no code generation, no build step. If you're comfortable with string column names and manual mapping, Queryflow is lighter. If you want compile-time safety, Queryflow can't provide it.

### 5. JAO (Just Another ORM)

**What it is:** A Django-inspired ORM for Dart. Supports PostgreSQL, SQLite, MySQL. Includes a CLI for migrations (`jao makemigrations`, `jao migrate`). Very new.

**How tables/models are defined:** Annotation-based with code generation (similar to stanza):

```dart
@Model()
class Author {
  @AutoField() late int id;
  @CharField(maxLength: 100) late String name;
  @EmailField(unique: true) late String email;
  @IntegerField(min: 0) late int age;
  @BooleanField(defaultValue: true) late bool isActive;
}
```

**How objects are created:** Code generation produces typed query interfaces. Results are mapped to model instances:

```dart
final authors = await Authors.objects
    .filter(Authors.$.age.gte(18) & Authors.$.isActive.eq(true))
    .orderBy(Authors.$.name.asc())
    .limit(10)
    .toList();
```

**Type safety:** Strong. Generated `$` accessor provides typed field references (`Authors.$.age`). Filter operations are typed to the field type (`.gte(18)` on an `IntegerField`). This is the closest competitor to stanza's approach.

**SQL completeness:** Appears comprehensive for basic CRUD. Supports `filter`, `exclude`, `orderBy`, `limit`, `offset`, `contains`, `startsWith`, `between`, `isNull`. Less clear on JOINs, RETURNING, upsert, aggregates.

**How stanza differs:** Both use annotations + code generation on plain Dart classes. The key differences:
- JAO is a full ORM with migrations, model lifecycle hooks (`beforeSave`, `afterDelete`), and Django-style manager pattern (`Authors.objects`). Stanza is deliberately a query builder — it generates SQL, not lifecycle management.
- JAO's filter API (`Authors.$.age.gte(18)`) is arguably more ergonomic than stanza's chained where clause (`..where(Author.$table.age).isGreaterThanOrEqualTo(18)`), since JAO's field accessors carry their type and expose only valid operations.
- JAO is very new with uncertain maintenance trajectory.

### 6. Prisma Client Dart (`orm` package)

**What it is:** A Dart port of Prisma ORM. Schema-first: you define your data model in a `.prisma` schema file, and it generates a type-safe Dart client.

**Current status:** Development suspended as of June 2025 due to Prisma's architecture change from Rust to TypeScript. Existing versions still work with older Prisma engine versions but will not be updated.

**How it works:** Entirely different paradigm. Schema is defined in Prisma's DSL (not Dart), and the Prisma Engine (a Rust binary) handles query execution. The Dart client is a thin wrapper that serializes queries to the engine.

**Not a real competitor** to stanza — different philosophy, external runtime dependency, and currently unmaintained.

---

### 7. DuxtORM

**What it is:** An ActiveRecord-style ORM for Dart. Supports PostgreSQL, MySQL, SQLite. Includes auto-migrations and soft deletes.

**How objects are created:** Subclass `Entity` and implement `toMap()` / factory constructor:

```dart
class User extends Entity {
  int? _id;
  String? email;
  String? name;
  bool isActive;

  @override
  Map<String, dynamic> toMap() => {
    'id': id, 'email': email, 'name': name, 'is_active': isActive ? 1 : 0,
  };
}
```

**Type safety:** Low. Query builder uses string column names (`users.where('role', 'admin')`). No code generation. Mapping is manual via `toMap()`.

**Not a strong competitor** — less type-safe than stanza, more boilerplate for entity mapping.

---

### 8. Fluent Query Builder (`fluent_query_builder`)

**What it is:** An older (2019-era) query builder for PostgreSQL and MySQL. No code generation.

**Type safety:** None. String-based everything. Manual `fromMap`/`toMap` on model classes.

**Not a strong competitor** — appears unmaintained, pre-null-safety API design.

## Stanza's Positioning

### What makes stanza unique

**1. Class-first design with code generation.**
You write a normal Dart class — the kind you'd use anywhere in your application — and annotate it. The generator creates the database interface *from* your class. This is the opposite of Drift (which generates classes from its table DSL) and Dartonic/Queryflow (which don't generate anything). Only JAO shares this approach.

The practical impact: your domain model is yours. You can use the same `Animal` class in your API serialization, your state management, and your database layer. You don't inherit from a framework base class (DuxtORM) or adapt to a generated row class (Drift).

**2. PostgreSQL-specific, not lowest-common-denominator.**
Every multi-database package (Dartonic, Queryflow, Drift, JAO) must restrict its API to features that work across SQLite, MySQL, and PostgreSQL. This means no PostgreSQL-specific syntax, no leveraging PG-specific performance features, and often a translation layer that introduces overhead or limitations.

Stanza can expose the full power of PostgreSQL without compromise: RETURNING, ON CONFLICT with full DO UPDATE, PG-specific types, PG-specific date/time handling, array types, JSONB operations — none of these need to be abstracted behind a compatibility layer.

**3. Query builder, not ORM.**
Stanza deliberately does not include migrations, lifecycle hooks, relationship management, lazy loading, or change tracking. This is a feature, not a limitation. It means:
- Smaller dependency footprint
- Less magic — the SQL stanza generates is predictable and inspectable
- Composable with other tools (you can use stanza for queries and a separate migration tool)
- Easier to understand and debug

For developers who want control over their SQL but don't want to write mapping boilerplate, this is the right level of abstraction.

**4. Compile-time field safety without schema duplication.**
Drift requires you to define your schema in its DSL *and* optionally map to your own classes. Stanza requires you to annotate your existing classes — no schema duplication. The generated `Field` getters give you compile-time safety on column references without a separate schema language.

### Where stanza is weakest

**1. Feature completeness.** Drift has years of development behind it. Stanza lacks JOINs, RETURNING, upsert, and many other features that Drift, Dartonic, and even Queryflow already support. The roadmap addresses this, but today it's a blocker for adoption.

**2. Ecosystem.** No tests, no CI, no pub.dev presence, no documentation beyond the example. Drift has extensive docs, a website, community, and hundreds of GitHub stars.

**3. One developer.** Drift is actively maintained by a dedicated author with years of investment. Stanza is a resurrection project. Prospective users will ask: "Will this still be maintained in a year?"

### The niche

Stanza's ideal user is a Dart/Flutter developer building a PostgreSQL-backed server-side application who wants:
- Type-safe queries without the overhead of a full ORM
- To keep their domain classes as plain Dart objects
- PostgreSQL-specific features without a multi-database abstraction penalty
- Predictable, inspectable generated SQL
- Something lighter than Drift but safer than raw `postgres`

This niche is currently unoccupied. Drift is too heavy for some use cases, raw postgres is too manual, and the other query builders (Dartonic, Queryflow) don't offer compile-time safety. If stanza can fill the feature gaps identified in the roadmap, it has a defensible position.
